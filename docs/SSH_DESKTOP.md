# Optional SSH access and Claude Desktop

This guide describes a manual extension for using the sandbox through SSH and the Claude Desktop Code tab. The default installer does not enable SSH. The steps below require local image changes and have not yet been validated end to end with this repository.

Terminal access through `./sandbox` remains the default. SSH is useful when an application needs an SSH connection to run commands inside the workspace.

## Connection model

```text
Mac terminal or Claude Desktop
  |
  +-- Mac SSH client
       |
       +-- Docker exec transport
            |
            +-- SSH server inside sandbox-workspace
                 |
                 +-- Container user, /workspace, persistent home
                      |
                      +-- Existing shared gateway network
```

The SSH client uses a `ProxyCommand` to start an SSH server over Docker's input/output streams for each connection. No SSH TCP port is published on the Mac, and no inbound route through the gateway is needed. The workspace still shares the gateway's network namespace for external requests.

Access to Docker on the Mac is required. The transport invokes the server as root so it can authenticate and switch users; the authenticated session runs as the configured non-root workspace user.

The following steps are specific to macOS and this repository's default `/home/sandbox` home directory.

## 1. Add the SSH server to the workspace image

In [`image/Dockerfile`](../image/Dockerfile), add `openssh-server` to the existing `apt-get install` package list. Keep `openssh-client` as well.

Create `image/sshd_config` with the following contents:

```text
HostKey /home/sandbox/.ssh/ssh_host_ed25519_key
PidFile /tmp/sshd-sandbox.pid
AuthorizedKeysFile .ssh/authorized_keys
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
PermitRootLogin no
UsePAM no
StrictModes yes
MaxSessions 10
AllowAgentForwarding no
AllowTcpForwarding local
AllowStreamLocalForwarding local
GatewayPorts no
PermitTunnel no
X11Forwarding no
PermitUserEnvironment no
PrintMotd no
SetEnv PATH=/home/sandbox/.local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin TZ=America/Los_Angeles LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8
Subsystem sftp internal-sftp
```

The `SetEnv` values match the repository defaults. If the workspace uses another timezone or locale, align these values with the workspace configuration before building. SSH command execution does not necessarily load the same shell startup files as an interactive terminal.

Add these lines to `image/Dockerfile`, before its `ENTRYPOINT`:

```dockerfile
COPY sshd_config /etc/ssh/sshd_sandbox_config
RUN mkdir -p /run/sshd
```

From the repository directory in a **Mac terminal**, stop active tasks and rebuild:

```bash
./sandbox down
./sandbox build
./sandbox up
```

These commands interrupt existing container sessions. Keep the same persistent state directory when recreating the containers.

## 2. Create a dedicated client key

On the **Mac**, create a key for this connection:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/claude_sandbox_ed25519 -C claude-sandbox
```

Choose a different filename if that key already exists; do not overwrite an existing key. If you set a passphrase, load the key into your SSH agent before using Desktop:

```bash
ssh-add ~/.ssh/claude_sandbox_ed25519
```

Keep the private key on the Mac. Only its `.pub` file goes into the workspace.

## 3. Initialize server identity and authorize the client

Run from the **Mac**, after the workspace is up:

```bash
docker exec -u 0 sandbox-workspace bash -c '
set -eu
uid="$SANDBOX_UID"
gid="$SANDBOX_GID"
user_name="$(getent passwd "$uid" | cut -d: -f1)"
test -n "$user_name"
# Permit public-key login for an account created without a password.
# Password authentication remains disabled in the SSH server config.
usermod -p "*" "$user_name"
mkdir -p /run/sshd /home/sandbox/.ssh
chown "$uid:$gid" /home/sandbox/.ssh
chmod 700 /home/sandbox/.ssh
if [ ! -f /home/sandbox/.ssh/ssh_host_ed25519_key ]; then
  ssh-keygen -t ed25519 -N "" -f /home/sandbox/.ssh/ssh_host_ed25519_key
fi
chmod 600 /home/sandbox/.ssh/ssh_host_ed25519_key
'
```

Install the client public key as the workspace user:

```bash
cat ~/.ssh/claude_sandbox_ed25519.pub | docker exec -i   -u "$(id -u):$(id -g)" sandbox-workspace sh -c '
set -eu
umask 077
touch /home/sandbox/.ssh/authorized_keys
cat >> /home/sandbox/.ssh/authorized_keys
chmod 600 /home/sandbox/.ssh/authorized_keys
'
```

This appends the key without replacing existing authorized keys. The UID/GID command assumes `.env` still uses the current Mac user's identifiers, as generated by the installer. If you customized them, use the configured values instead.

Check the server configuration and record its fingerprint:

```bash
docker exec -u 0 sandbox-workspace /usr/sbin/sshd -t -f /etc/ssh/sshd_sandbox_config
docker exec -u 0 sandbox-workspace ssh-keygen -lf /home/sandbox/.ssh/ssh_host_ed25519_key.pub
```

The first command should exit successfully without output. The second prints the fingerprint to compare at first connection. Server keys and authorized client keys remain under the persistent home directory across container recreation. A newly recreated container may need the account initialization command above again; the default entrypoint does not perform SSH initialization.

## 4. Add a Mac SSH alias

Find the Docker executable and workspace login name from the **Mac**:

```bash
command -v docker
docker exec sandbox-workspace getent passwd "$(id -u)"
```

The first field of the passwd entry is the login name. Do not assume it is the Mac username, `dev`, or `sandbox`: the entrypoint can reuse an existing account with the configured UID.

Add a block to `~/.ssh/config`, before any broad `Host *` defaults that might conflict:

```sshconfig
Host claude-sandbox
    HostName claude-sandbox-container
    User REPLACE_WITH_CONTAINER_LOGIN_NAME
    IdentityFile ~/.ssh/claude_sandbox_ed25519
    IdentitiesOnly yes
    HostKeyAlias claude-sandbox-container
    UserKnownHostsFile ~/.ssh/known_hosts_claude_sandbox
    ForwardAgent no
    ProxyCommand /ABSOLUTE/PATH/TO/docker exec -i -u 0 sandbox-workspace /usr/sbin/sshd -i -e -f /etc/ssh/sshd_sandbox_config
```

Replace the login name and Docker path using the command output. The `HostName` is a label for this transport; it does not need a DNS entry because Docker carries the connection. No `Port` setting is needed.

```bash
chmod 600 ~/.ssh/config
ssh claude-sandbox
```

At first connection, compare the displayed host fingerprint with the one printed directly from the container before accepting it. Do not disable host-key checking to resolve a mismatch.

## 5. Use the terminal connection

After connecting:

```bash
cd /workspace
id
printf '%s\n' "$HOME"
```

Expect the configured non-root user and `/home/sandbox`. If Claude Code has already been installed using the README steps:

```bash
claude
```

Run `exit` to leave the SSH session. This does not stop the containers.

Before using Desktop, check file transfer from a **Mac terminal** as well:

```bash
sftp claude-sandbox
```

A successful connection shows an `sftp>` prompt. Enter `quit` to close it.

## 6. Connect Claude Desktop

Claude Desktop's Code tab supports SSH environments, including connections defined in the Mac's `~/.ssh/config`. It requires a working SSH server with SFTP and a writable, executable home directory for its remote components. See the [official SSH session documentation](https://code.claude.com/docs/en/desktop#ssh-sessions).

Once terminal SSH and SFTP work:

1. Open Claude Desktop, sign in, and open the **Code** tab.
2. Use the environment selector to add an SSH connection.
3. Use the connection name `Claude sandbox` and SSH host `claude-sandbox`. Leave port and key overrides empty to use the SSH configuration.
4. Select `/workspace` as the remote project folder and create the environment.

Labels may differ between Desktop versions. Desktop manages its own remote Claude Code installation; the terminal CLI version may differ. See the [official remote requirements](https://code.claude.com/docs/en/desktop#remote-machine-requirements-for-ssh-sessions).

Use the remote terminal to check `id`, `$HOME`, and the selected project path. Confirm the user and persistent home match the terminal SSH connection. If the session uses a Git worktree, its working directory can differ from `/workspace`.

Desktop's interface runs on the Mac. Commands started in the SSH environment run inside the container. Desktop and browser traffic on the Mac still use the Mac's own network settings; this connection does not put the entire desktop application behind the container gateway.

Do not assume that signing in to the Mac CLI, signing in to the container CLI, and signing in to Desktop are interchangeable. Follow the authentication prompts shown for each surface.

## 7. Everyday use and troubleshooting

Start Docker Desktop, then run `./sandbox up` from the repository before connecting through SSH or Desktop. If you stop or recreate the containers, active SSH sessions disconnect; reconnect after startup completes.

| Symptom | Check |
|---|---|
| Docker command not found from Desktop | Use the actual absolute Docker path in `ProxyCommand` |
| Container not running | Start the stack with `./sandbox up` |
| SSH closes immediately | Read the SSH error; check the server config, host keys, `/run/sshd`, and account initialization |
| Permission denied (publickey) | Check the login name, client key, authorized key, file ownership, and permissions |
| Terminal SSH works but Desktop cannot connect | Test SFTP and noninteractive execution with `ssh claude-sandbox 'id; echo "$HOME"'` |
| Host-key mismatch | Verify whether the persistent home changed and compare the server fingerprint directly |
| Commands cannot reach external services | Run `./sandbox verify` on the Mac; SSH connectivity alone does not validate outbound networking |

Before calling this extension supported, verify terminal SSH, SFTP, a Desktop session, persistence after container recreation, and the existing kill-switch check with SSH enabled. No SSH setup described here is run by `install.sh` today.
